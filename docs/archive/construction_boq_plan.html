Section 01

Industry Analysis

Current Workflow Reality

The typical construction estimator in Pakistan — whether a quantity surveyor at a mid-sized firm or a small contractor working residential projects — operates with a combination of printed rate schedules, WhatsApp price queries, and multi-tab Excel workbooks that took years to build. These files are irreplaceable, deeply personal, and completely opaque to anyone else. The workflow is: receive drawings, manually decompose into work items, look up market rates from memory or a phone call, type quantities, build SUBTOTALs in Excel, format a report, and email a PDF. This process takes 2–5 days for a mid-sized project and is error-prone at every step.

Excel Dependency — Why It Persists

Why they love it
Fully flexible formula system. Muscle memory built over years. No license cost. Prints reasonably well. Can share as attachment. Familiar to all parties in the project chain.
Why it breaks down
No version history. Easy to corrupt. Formulas break silently. No audit trail. Sharing creates conflicts. Formatting takes enormous time. No client-facing templates. No rate database.

Pain Points by Role

Small Contractors
Price Certainty
They underbid or overbid because rates are guesswork. No system to track actual vs. estimated. Lose money silently on jobs.
Quantity Surveyors
Report Quality & Time
Spend 30–40% of their time on formatting and layout. Client-facing reports look inconsistent. Revision requests mean rebuilding from scratch.
Home Builders
Budget Overruns
No single source of truth for the project budget. Contractors give verbal quotes. No way to compare or verify. Final cost 20–40% over estimate is common.

Pakistan/South Asia Specific Problems

Market Rates Fluctuate Weekly. Steel, cement, and labour rates in Pakistan change with dollar exchange rate, import duty changes, and seasonal demand. Any rate database must be manually updatable and locally controlled — not pulled from a cloud API that might go stale or be irrelevant.

Urdu/English bilingual workflows: Many contractors label materials in Urdu but reports must go to clients in English. The tool should support both scripts without fighting the user.

Pakistan Standard Specifications (PSS) and PHED/NHA rate schedules are government-issued documents that quantity surveyors reference constantly. Pre-loading these as importable templates is a strong differentiator. No existing tool does this for Pakistan specifically.

Trust deficit toward software: Estimators fear that "the computer got it wrong." They want to see every formula. Hiding calculations in black boxes will kill adoption. The UI must show working, not just totals.

Intermittent power and connectivity: Load shedding is real. The app must survive sudden shutdowns gracefully with autosave. Offline-first is not a nice-to-have — it is a hard requirement.

Existing Software Problems

Global tools (CostX, Candy, ARES)
$2,000–$15,000/year. English-only. Built for Western markets. No Pakistan rate schedules. Overly complex. Require multi-week training. Completely inaccessible for small contractors.
Local Excel templates (sold on OLX/Daraz)
One-time PKR 500–2,000. No updates. Break when Excel version changes. No database. No export. Sold by random individuals with no support. Trust is zero.

Section 03

Product Vision

"The professional construction estimator's workbench — as fast as Excel, but built for Pakistan's construction reality."

Core Vision

A desktop-first application that replaces the estimator's Excel workbook without requiring them to change how they think. The app behaves like a spreadsheet but stores data properly, enforces calculations correctly, and produces client-ready reports in one click. It works without the internet, survives load shedding, and costs less than a day's labour.

Biggest Pain Solved

The transition from raw quantities to a professional, printable, client-ready BOQ currently takes 30–60% of an estimator's time due to formatting. This app collapses that to zero. You enter data; the report formats itself.

Why Users Would Switch from Excel

They won't "switch" — the app must feel like an upgrade of Excel, not a replacement. The first session should let them import their existing Excel rates. The interface must use the same mental model: rows, columns, formulas, totals. The switching cost must feel like zero.

Competitive Advantage

Localization Moat
PSS specs, PHED rates, city-level pricing for Lahore/Karachi/Islamabad/Peshawar pre-loaded. No global tool will ever invest in this.
Offline-First Architecture
SQLite on-device. Zero dependency on servers. No subscription anxiety. No data leakage fear.
Price Point
PKR 5,000–15,000 one-time license. Affordable for individual contractors. Incomparable to $5,000/year alternatives.

Long-Term Moat

The rate database grows richer with every user update. The template library becomes an ecosystem. Power users become evangelists in WhatsApp contractor groups. Network effects in a niche market are extremely sticky.

Section 06

Technical Architecture

Electron vs Tauri — Use Tauri

Electron
Ships Chromium + Node.js with every install. Installer: ~120MB. Memory: 200–400MB baseline. Well-documented. Every JS library works. But too heavy for low-spec Pakistani laptops.
✓ Tauri (Recommended)
Uses system WebView. Installer: ~3–8MB. Memory: 30–80MB baseline. Rust backend handles SQLite natively via tauri-plugin-sql. System file dialogs for save/open. Fast startup. Better for target market hardware.
Tauri caveat: Tauri's WebView uses the OS WebView (WebView2 on Windows, WebKit on macOS). Test AG Grid thoroughly on Windows 10/11 WebView2. Minor rendering differences exist but are manageable. The performance and binary size gains are worth it.

Frontend Module Structure

src/ ├── features/ │ ├── projects/ ← Project CRUD, dashboard │ ├── boq/ ← BOQ table, AG Grid config, cell editors │ │ ├── BoqGrid.tsx │ │ ├── BoqToolbar.tsx │ │ ├── columnDefs.ts │ │ ├── cellEditors/ │ │ └── hooks/useBoqData.ts │ ├── rates/ ← Material rate library │ ├── templates/ ← Template CRUD │ ├── export/ ← PDF + Excel engines │ └── settings/ ← Company profile, defaults ├── lib/ │ ├── db.ts ← Tauri SQL plugin wrapper │ ├── calculator.ts ← Pure calculation functions │ ├── validator.ts ← Input validation │ └── formatter.ts ← Number/currency formatting ├── store/ │ ├── projectStore.ts ← Zustand slice │ ├── boqStore.ts │ └── rateStore.ts └── components/ ← Shared UI (Button, Modal, etc.)

State Management — Zustand (not Redux)

Redux is overkill. Use Zustand for simple, colocated state. Each feature has its own store slice. The BOQ store holds the current project's line items in memory. On every change, it calls the DB write (debounced 500ms). AG Grid reads from Zustand, not directly from SQLite — this gives instant UI updates.

Autosave Strategy

User edits cell → Zustand state updates instantly (AG Grid re-renders) → debounce(500ms) triggers → db.saveBoqItem(item) → title bar shows "Saved ✓" indicator → On app close: force flush any pending saves → On crash recovery: read last state from SQLite (it's always current)

Backup Strategy

The SQLite file lives at %APPDATA%/BoqCalculator/db.sqlite on Windows. Settings menu exposes a "Backup Now" button that copies this file to a user-chosen folder with a timestamp. Optional: auto-backup on each export action. Educate users to add this folder to their Google Drive or USB stick routine — don't build cloud sync for MVP.

Section 08

BOQ Calculation Engine

Architecture Principle — Pure Functions, No Side Effects

The entire calculation engine lives in src/lib/calculator.ts as pure TypeScript functions. They receive data in, return computed data out. No database calls, no UI updates, no side effects. This makes them trivially testable and debuggable.

Core Calculation Flow

// Per-item calculation
amount = round(quantity × rate, 2)

// Section subtotal
sectionSubtotal = sum(amounts of all items in section)

// Project totals
subtotal = sum(all section subtotals)
contingency = round(subtotal × contingencyRate, 2) // optional %
netTotal = subtotal + contingency
tax = round(netTotal × taxRate, 2) // GST 17% Pakistan
grandTotal = netTotal + tax

// With profit margin (for contractor use)
profitAmount = round(netTotal × profitMarginRate, 2)
grandTotal = netTotal + tax + profitAmount

Quantity Dimensions Sub-Calculator

For items like "Excavation in Foundation" the quantity is derived from dimensions. Each item can have child rows (L, W, H, No.) that multiply to produce the quantity. This mirrors how QS textbooks teach it.

// Dimension rows for one item:
Row 1: Foundation Strip No=4, L=8.5m, W=0.6m, H=1.2m → 24.48 m³
Row 2: Column Pits No=12, L=1.0m, W=1.0m, H=1.5m → 18.00 m³
Total Quantity = 42.48 m³

Rounding Policy

Quantities
3 decimal places for volumes (m³). 2 decimal places for areas and lengths. 0 decimals for countable items (Nos). User-configurable per unit type.
Currency Amounts
Always 2 decimal places. Round half-up (Math.round). Never truncate. Store full precision in DB, display rounded. Grand total rounds to nearest 1 PKR.

Validation Rules

Silent errors kill trust. Every validation failure must be visible on the cell — red border, tooltip. Never silently zero-out or auto-correct without telling the user.
Quantity
Must be ≥ 0. Warn (not error) if 0 — might be intentional placeholder. Cannot be negative. Non-numeric input = instant red border.
Rate
Must be ≥ 0. Warn if 0 or if rate deviates >50% from library rate for same item — possible typo.
Unit
Must be a recognised unit string. Provide dropdown of valid units. Free-text allowed but flagged as custom.
Description
Required field. Warn if item is non-section-header with empty description before export.
Section 09

Export System

PDF Export — Use @react-pdf/renderer

@react-pdf/renderer runs entirely in the browser process (no server needed). You define your report as React components using its PDF primitives (<Document>, <Page>, <View>, <Text>). It generates a proper vector PDF — not a screenshot. This is critical for professional output.

Alternative: If @react-pdf/renderer has performance issues with large BOQs (500+ items), fall back to Puppeteer via Tauri sidecar — render an HTML report page headlessly and print to PDF. More setup but handles any complexity.

PDF Report Structure

Page 1 — Cover
Company logo top-left. Project name large. Client name. Site address. Date prepared. Revision number. Prepared by (QS name). For (client). Total amount summary box.
Pages 2–N — BOQ Table
Columns: Item No | Description | Unit | Qty | Rate (PKR) | Amount (PKR). Section headers as full-width shaded rows. Running total in footer. Page number top-right.
Final Page — Summary
Subtotals by section. Contingency. Net total. GST. Grand total. Signature blocks: Prepared by / Checked by / Approved by.
Appendix (optional)
Rate analysis page showing material breakdowns for key items. Useful for government tenders.

Excel Export — Use SheetJS (xlsx)

SheetJS is the industry standard for browser-side Excel generation. It handles styles, merged cells, formulas, and column widths. The exported file should include actual Excel formulas for Amount (=C×D) so the client can verify calculations in Excel — this builds trust.

SheetJS approach:
1. Map boq_items to row array
2. Create worksheet with aoa_to_sheet()
3. Set column widths, row heights
4. Style section header rows (bold, background color)
5. Add SUM formulas for subtotals
6. Add TOTAL, TAX, GRAND TOTAL rows with borders
7. write() → ArrayBuffer → Tauri fs.writeBinaryFile()

AI Integration Strategy

Ground rule: AI features must work without the internet for the MVP target market. Cloud AI APIs are a Phase 3 premium feature. The core product must be 100% functional offline.

Realistic MVP AI (Phase 2–3)

Smart Description Autocomplete
Fuzzy search on local rate library
Not true AI — but feels like it. As user types "brick", show top 5 matching items from rate library with their rates. One Tab key to accept. This is the highest-value "AI feel" with zero complexity.
Rate Anomaly Detection
Statistical outlier warning
If user enters a rate that's 3x the library average for that item, show a warning: "This rate seems unusual. Library average: PKR 850/m³." Simple statistics — no model needed.

Phase 3 AI — Cloud API (Optional, Premium)

AI Item Generation
User types: "2-bedroom residential house, ground floor slab." AI returns a structured list of BOQ items with quantities, units, and suggested rates. Powered by Claude or GPT-4 API call. User reviews and accepts each item.
Document Extraction
User uploads a PDF spec sheet or old Excel BOQ. AI extracts items, quantities, and rates into a draft BOQ. Massive time saver for legacy project conversion. Powered by Claude's document understanding.

Phase 4 AI — Local LLM with Ollama

For users who cannot or will not send data to the cloud: integrate Ollama as a Tauri sidecar process. A small 7B model (Mistral, Llama 3.2) running locally can power item generation and description suggestions entirely offline. Requirements: 8GB RAM, but this is increasingly common. This becomes a strong privacy-first selling point for government and institutional clients.

What NOT to Build in AI

Do not build drawing recognition/OCR from architectural plans in Phase 1 or 2. This requires training data, computer vision models, and months of engineering. It is 2–3 years of roadmap, not an MVP feature. Mention it in marketing as "coming soon" — do not promise it to users.

Section 13

Risk Analysis

AG Grid ComplexityHIGH
AG Grid is powerful but has a steep configuration curve. Cell editors, row dragging, section headers, and keyboard navigation all require significant custom code. Underestimating this will double your BOQ screen development time.
Mitigation: Prototype the BOQ grid before building anything else. Spend 1 week on a standalone AG Grid proof-of-concept with all required behaviors. This de-risks the entire frontend.
Tauri WebView InconsistenciesMEDIUM
Tauri uses OS WebView2 on Windows. Older Windows 10 machines (common in Pakistan) may have outdated WebView2. Rare CSS/JS bugs that don't appear in Chrome.
Mitigation: Bundle WebView2 installer with your app. Test on Windows 10 1903 virtual machine. Stick to well-supported CSS features. Avoid cutting-edge CSS Grid subgrid, container queries in MVP.
"Excel is good enough" ObjectionHIGH
The most dangerous adoption barrier is not awareness — it's inertia. The person who has used Excel for 10 years does not feel the pain acutely. They've adapted. Only the report formatting pain point is truly universal and cannot be solved with Excel.
Mitigation: Lead all marketing with the PDF report quality angle. Show the before/after of report formatting time. Do not lead with "it's better than Excel" — lead with "it produces better reports, faster."
PiracyMEDIUM
Software piracy is common in Pakistan. A cracked version of your tool could circulate freely within weeks of launch.
Mitigation: Use simple device fingerprint-based license key (not complex DRM — it fails). Price affordably enough that cracking is not worth the effort. Focus on value-adds that require legitimate ownership: updates, support, new templates, community access.
Scope CreepHIGH
As a solo developer, every user request feels urgent. Early users will ask for mobile app, cloud sync, WhatsApp integration, drawing import, and 50 other features. Building all of them kills the product before it launches.
Mitigation: Maintain a public roadmap on Notion or Trello. Tell users "it's on the roadmap for Phase X." Never promise delivery dates. Build only what moves the core metric: reports produced per day.
Data Loss Trust IncidentsHIGH
If a user loses a project due to a bug, they will tell every person in their network. One data loss story on a WhatsApp group can kill months of growth.
Mitigation: Autosave every 500ms. Create automatic timestamped backup on every export action. Never delete projects — archive them. Build a "recover last session" feature before launch. Treat data integrity as your #1 engineering priority.
